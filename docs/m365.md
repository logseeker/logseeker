# Microsoft 365 監査ログの取り込み

Microsoft 365 の統合監査ログ（Exchange・SharePoint・OneDrive・Teams・Entra ID のサインインと管理操作など）を
`source_type = m365_audit` として取り込み、検知ルール（`[M365]`）の対象にする。

取り込み方は2つある。どちらも同じ取り込み口（`backend/app/m365_audit.py`）を通るので、結果は同じになる。

| 方法 | 使う場面 | 取れる範囲 |
|---|---|---|
| コネクタ（画面「外部連携」） | 普段の運用。定期的に自動で取得する | 過去7日まで（Microsoftの仕様） |
| CSV取り込み（コマンド） | コネクタを設定する前の期間を入れる | Purviewで検索できる範囲（既定180日） |

同じレコード（監査レコードの `Id`）は二度入らない。CSVとコネクタで期間が重なっても、CSVを何度取り込んでも重複しない。

## コネクタの設定

### 1. Entra ID でアプリを登録する

1. Microsoft Purview で監査が有効になっていることを確認する（既定で有効）
2. Entra 管理センター → 「アプリの登録」 → 「新規登録」（名前は任意。リダイレクトURIは不要）
3. 「APIのアクセス許可」 → 「アクセス許可の追加」 → 「Office 365 Management APIs」 → 「アプリケーションの許可」で
   `ActivityFeed.Read` を追加する（DLPも取る場合は `ActivityFeed.ReadDlp` も）
4. 「<テナント名> に管理者の同意を与えます」を押す
5. 「証明書とシークレット」 → 「新しいクライアントシークレット」を作り、**値**を控える（シークレットIDではない）

シークレットには有効期限がある。期限が来る前に新しいものを作り、画面で入れ替えること（期限切れになると取得が失敗し、
画面の「最終取得」にエラーが出る）。

### 2. LogSeeker の画面で設定する

左メニューの「外部連携」（システム管理者のみ）で、テナントID（ディレクトリID）・クライアントID（アプリケーションID）・
クライアントシークレットを入れて保存し、「接続テスト」を押す。接続テストはトークンの取得と購読状況の確認だけで、
取り込みはしない。

「自動取得を有効にする」をオンにすると、設定した間隔（既定15分）で取得する。「今すぐ取得」で手動でも動かせる。

- 初回は過去7日分を取得する。購読を開始したばかりの種別は、ログが届き始めるまで最大12時間ほどかかる
- Microsoft側で監査レコードが取得できるようになるまで、操作から数十分〜最長24時間ほど遅れることがある
- 取得するログの種類（コンテンツ種別）は画面で選べる。既定は DLP 以外の4種類

| 種類 | 主な内容 |
|---|---|
| Audit.AzureActiveDirectory | サインイン（UserLoggedIn / UserLoginFailed）、ユーザー・アプリ・ロールの管理操作 |
| Audit.Exchange | メールボックスの操作（MailItemsAccessed 等）、受信トレイルール、管理コマンド（Set-Mailbox 等） |
| Audit.SharePoint | SharePoint / OneDrive のファイル操作・共有 |
| Audit.General | Teams・Copilot・Defender for Office 365（TIMailData）等 |
| DLP.All | DLPポリシーによる機密情報の検出（機密情報の内容を含むため既定では取らない） |

クライアントシークレットは settings テーブルに保存し、画面・APIには返さない（「設定済み」かどうかだけを返す）。
GCC 等の別クラウドを使う場合は、環境変数 `M365_LOGIN_BASE` / `M365_API_BASE` で接続先を変える
（例: GCC は `M365_API_BASE=https://manage-gcc.office.com`）。

## CSVの取り込み

Microsoft Purview → 「監査」 → 検索 → 「エクスポート」で出したCSV（列: RecordId, CreationDate, RecordType, Operation,
UserId, AuditData, …）を取り込む。使うのは `AuditData` 列（APIが返すJSONと同じもの）だけ。

```bash
# 開発（Docker。CSVは data/ 配下など、コンテナから見える場所に置く）
docker exec logseeker-backend-1 python -m app.tools.import_m365_csv /app/data/m365/audit.csv

# 本番（ネイティブ）
cd /opt/logseeker/backend && sudo -u logseeker ../venv/bin/python -m app.tools.import_m365_csv /path/to/audit.csv

# 書き込まずに件数・期間・未取り込みの件数だけ確認する
... -m app.tools.import_m365_csv --dry-run audit.csv
```

- 1,000件ごとにcommitする。10万件で約100秒（開発環境で計測）
- 5万行ちょうどのCSVは、Purviewのエクスポートの上限で期間の途中で切れている可能性がある（ツールが警告を出す）。
  その場合は期間を分けてエクスポートし直す
- JSONとして読めない行は「取り込み失敗」（dead_letters）に入る
- 取り込んだイベントの受信日時（received_at）は取り込んだ時刻になる。保持期間による自動削除も受信日時で決まるので、
  古いログを取り込んでもすぐには消えない。一方で、検知ルールの評価期間（既定は受信から24時間）にまとめて入るため、
  大量に取り込んだ直後は、件数で判定するルール（大量ダウンロード等）が期間をまたいだ合計で発火することがある

## 送信JSONの形（Taxonomy KEYへの対応）

コネクタとCSV取り込みツールは「ログ送信元」として、Microsoftの監査レコードを既存のTaxonomy KEYで組み立てたJSONにして
取り込む（`m365_audit.to_payload`。`docs/taxonomy.md` v1.15 §6.8）。FireEye Helix が Office 365 を `action`・`username`・
`srcipv4` 等の共通KEYで扱うのと同じ考え方で、MicrosoftのKEY名（`ClientIP`・`Operation` 等）はTaxonomyに加えない。
監査レコード全体は `rawmsg` に無改変の文字列（区切りに空白の無いJSON）として残す。

| Taxonomy KEY | 監査レコードのKEY |
|---|---|
| `class` | `m365_audit`（送信元として設定） |
| `eventtime` | `CreationTime`。タイムゾーン表記の無いUTCなので末尾に `Z` を付ける |
| `service` | `Workload`（Exchange / SharePoint / OneDrive / MicrosoftTeams / AzureActiveDirectory 等） |
| `action` | `Operation`（MailItemsAccessed / UserLoggedIn / New-InboxRule 等） |
| `username` | `UserId`（システム処理では NT SERVICE\… や SID、アプリのID等） |
| `srcipv4` / `srcipv6` | `ClientIP` → `ClientIPAddress` → `ActorIpAddress` の順に、IPとして読める最初の値。`[IPv6]:ポート`・`IPv4:ポート`・`::ffff:IPv4` からはIPだけを取り出し、`NA` やループバック（`[::1]`）は捨てる |
| `result` | `ResultStatus` |
| `objectname` | `ObjectId` |
| `errorcode` / `failurereason` | `ErrorNumber` / `LogonError` |
| `useragent` / `application` / `appid` | `UserAgent` / `ApplicationDisplayName` / `ApplicationId`（無ければ `ClientAppId`・`AppId`） |
| `filename` / `filepath` | `SourceFileName` / `SourceRelativeUrl` |
| `mailbox` / `subject` / `mailfrom` | `MailboxOwnerUPN` / `Subject` / `P1Sender` |
| `parameters` / `modifiedproperties` / `extendedproperties` / `target` / `sessionid` / `deviceid` | 同名のKEY |
| `rawmsg` | 監査レコード全体 |

`SiteUrl` は `url` に入れない（`url` は汎用の正規化でWebのパスの列になり、危険パス等のWeb用ルールにSharePointのURLが
掛かってしまうため）。上に無い値（`OperationProperties`・`Verdict`・`DeliveryAction` 等）は `rawmsg` にあり、
全文検索と、ルールでの `rawmsg` の正規表現で使う。

MicrosoftのJSONを別の経路でそのまま `/ingest` へ送った場合、そのKEYはTaxonomy外KEYになり、画面にも検知にも使われない
（LogSeekerは受信後にKEYを読み替えない）。M365のログはコネクタかCSV取り込みツールで入れること。

## 正規化（events の列）

`event_time`（`eventtime`）・`source_ip`（`srcipv4`/`srcipv6`）・`actor_user`（`username`）・`service_name`（`service`）は
汎用のTaxonomy KEYの優先順で入る。M365の分岐（`m365_audit.normalize_m365`）で決めるのは次の列。

| 列 | 値 |
|---|---|
| event_action | `action` |
| event_category | サインイン（UserLoggedIn / UserLoginFailed）は authentication、それ以外は audit |
| event_result | 下記 |
| source_name | Microsoft 365（ログソース名 `m365` の場合） |
| message | `service / action: 対象`（対象は `filename` → `objectname` の順） |

event_result:

- UserLoggedIn は success
- UserLoginFailed は、資格情報が通らなかったエラー番号（50126 パスワード誤り、50053 ロック、50034 ユーザーなし、
  50057 無効、500121 MFAの失敗・拒否、53003 条件付きアクセスでブロック 等）だけを failure にする。
  それ以外（50074 MFAを求めるための中断、50199 確認画面、65001 アプリの同意なし、50055 パスワードの期限切れ 等）は、
  Microsoftの記録上は UserLoginFailed でも通常のサインインの途中経過なので unknown にする。
  実テナントのデータでは UserLoginFailed 105件のうち、資格情報の失敗は19件だった
- それ以外の操作は `result`（ResultStatus）から（Succeeded / Success / Successful / True → success、
  Failed / Failure / Error / AuthorizationFailure / False → failure、値なし・PartiallySucceeded → unknown）

## 検知ルール（ルールパック `[M365]`）

`backend/app/rulepacks/builtin.yaml` の18ルール。

| ルール | 重大度 | 条件 |
|---|---|---|
| パスワードスプレーの疑い | high | 同じIPから5アカウント以上でサインイン失敗（資格情報の失敗のみ） |
| MFAの失敗・拒否の繰り返し | high | 同じユーザーでエラー500121が3回以上 |
| 海外からのサインイン | high | UserLoggedIn の送信元の国が日本以外（GeoLite2-Country.mmdb が必要） |
| 転送・削除をする受信トレイルール | high | New-InboxRule / Set-InboxRule / UpdateInboxRules で転送・リダイレクト・削除の動作 |
| 受信トレイルールの作成・変更 | info | 受信トレイルールの作成・変更すべて |
| メールボックスの自動転送の設定 | high | Set-Mailbox で ForwardingSmtpAddress / ForwardingAddress に値 |
| メールフロールールの作成・変更 | warning | New-/Set-/Remove-/Enable-/Disable-TransportRule |
| メールボックスのアクセス権の付与 | warning | Add-MailboxPermission / Add-RecipientPermission（Exchangeのシステム処理を除く） |
| 管理者ロールの付与 | high | Add member to role. 等 |
| アプリへの同意 | warning | Consent to application. |
| アプリへの資格情報の追加 | warning | Add service principal credentials. 等 |
| ユーザーの追加・削除・パスワードリセット | info | Add user. / Delete user. / Reset user password. 等 |
| 条件付きアクセスの変更 | warning | Add / Update / Delete conditional access policy. |
| 監査ログの無効化 | critical | UnifiedAuditLogIngestionEnabled・AuditEnabled を False、AuditBypassEnabled を True 等 |
| 匿名の共有リンクの作成 | warning | AnonymousLinkCreated / AnonymousLinkUpdated |
| ファイルの大量ダウンロード | warning | 1ユーザーで200件以上（app@sharepoint を除く） |
| ファイルの大量削除 | warning | 1ユーザーで100件以上（SHAREPOINT\system を除く） |
| フィッシング・マルウェアメールの配信 | high | TIMailData で Verdict が Phish / Malware かつ DeliveryAction が Delivered |

確認したこと（2026-10-22、開発環境）:

- 実テナントの監査ログ約10万件（2026-08-01〜10-15）で、日ごとに区切ると件数系のルールはどれもしきい値に届かなかった
  （同じIP・同じ日の失敗ユーザー数は最大3、1人1日のダウンロードは最大79件、削除は最大12件）。
  発火したのは「受信トレイルールの作成・変更」「アプリへの同意」「ユーザーの追加・削除・パスワードリセット」で、
  いずれも実際に行われた操作だった
- 18ルールすべてについて、模擬イベントで発火すべきケースで発火し、発火すべきでないケース
  （MFAの中断・期限切れのサインイン失敗、転送の解除、Exchange / SharePoint のシステム処理、しきい値の1件手前、
  迷惑メールフォルダーへの配信、IntuneのMDMポリシーの更新）で発火しないことを確認した
- 「条件付きアクセスの変更」「管理者ロールの付与」「アプリへの資格情報の追加」「監査ログの無効化」「匿名の共有リンク」
  「メールフロールール」「フィッシングの配信」は、実データに該当する操作が無く、Microsoftの公開仕様の操作名で書いている

M365 は組み込みルールのうち次の2つの対象から外している（`rules.py`）。

- **失敗のあとにログイン成功（auth_success_after_failure）**: 会社の出口IPを社員全員で共有するため、別々の人の
  打ち間違いが1つの送信元にまとまり、実データでは誤検知しか出なかった
- **海外からのアクセス（foreign_access）**: アプリ経由のメール・ファイル操作の接続元はMicrosoftのサービスのIP
  （MailItemsAccessed の大半が 20.190.x / 40.126.x）で、利用者の居場所を表さない。M365はサインインに限って
  「[M365] 海外からのサインイン」で見る

## データ量の目安

実テナント（利用者10人弱）で1日400〜6,000件、1件あたり約2.4KB（AuditData のJSON）。
件数の大半は MailItemsAccessed（メールの閲覧。約4割）と、Teams・SharePoint の閲覧系の操作。
